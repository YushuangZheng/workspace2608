# 双臂关系门控恢复开发报告

## 1. 研究位置与结论边界

真实物理交接专家和双臂在线关系估计已经分别通过冻结门槛，因此本阶段开始回答一个更窄的
问题：检测到接收边未建立或已断裂后，能否把关系事件转化为安全、有限、可解释的运行时
恢复。这里没有训练新的神经策略，也不把脚本专家称为完整双臂 DynaMAC。新增机制是位于
冻结专家之上的关系恢复监督层；其作用是冻结任务时钟、覆盖局部动作、重新抓取并从实测
位姿恢复原任务。

## 2. 四种方法与五种条件

四种方法共享同一个真实物理环境、脚本专家、动作接口和故障注入：

| 方法 | 控制使用的关系 | 关系门 | 几何恢复 |
| --- | --- | --- | --- |
| `clocked_expert` | 无 | 无 | 无 |
| `relation_gate` | 在线估计 | 有 | 无 |
| `relation_recovery` | 在线估计 | 有 | 有 |
| `oracle_relation_recovery` | 当步物理真值 | 有 | 有 |

Oracle 只替换当前步的左右关系状态，不提供目标动作、不读取未来观测。恢复位姿仍由当前末端、
物体和目标位姿计算。在线方法的控制关系边逐步保存到 NPZ，硬审计要求它与估计器输出完全
一致；Oracle 的控制关系边必须与当步物理真值一致。

五种条件为：

1. `normal`：无故障；
2. `receiver_miss_once`：右夹爪首次闭合时强制张开并偏移 0.8 s；
3. `receiver_brief_loss`：共同持物期间强制张开并轻微偏移 0.12 s；
4. `receiver_loss_once`：共同持物期间强制张开并偏移 0.8 s；
5. `receiver_loss_after_release`：左臂真实释放后，右臂运输早期强制张开并偏移 0.8 s。

第五个条件专门排除“左臂一直兜底”的解释。故障成立不能只看动作命令：审计还要求右边
物理关系真实断裂；第五个条件额外要求故障开始时左边已经物理断开。

## 3. 恢复图与安全约束

恢复监督层与专家 phase 分离，状态为：

```text
NORMAL
  ├─ 空抓 → RECEIVER_MISS_DETECTED
  └─ 丢失 → RECEIVER_LOSS_DETECTED
               ↓
SAFE_RETREAT → REAPPROACH → REGRASP
               ↓                 ↓
        VERIFY_BOTH 或 VERIFY_RECEIVER
               ↓
          RESUME_TASK
```

主要约束如下：

- 右臂关系未稳定建立前，冻结 phase clock，左臂不得按时钟释放；
- 关系刚丢失时立即冻结，但等待 15 步（0.30 s）再进入几何恢复；若短故障自行恢复，则取消
  撤离和重抓；
- 左臂仍连接时，恢复期间保持左臂闭合，并要求 `VERIFY_BOTH`；
- 左臂已经释放时，不伪造 giver 边，只要求 `VERIFY_RECEIVER`；
- 最多两次重抓，总恢复不超过 600 步，每个恢复状态不超过 220 步；
- 双臂监督动作位置目标在最终输出层逐步限幅为 0.05 m；
- 恢复成功后，以实测末端—物体变换重置冻结专家的共享运输或接收臂运输轨迹，不修改
  已冻结的 `bimanual_physical.py`。

## 4. 开发反例如何改变实现

第一轮完整开发矩阵使用 seed 8603–8605，共 48 条、全部物理故障成立，summary SHA-256 为
`72133cc42f43dff94eadb51df23458d2190b5d656670194647ff423a40545389`。在线和 Oracle 恢复在
原四条件上均成功，但 0.12 s 短故障每次都进入了约 1 s 的完整撤离和重抓。与此同时，单纯
关系门控在该条件下可以等待关系恢复并完成任务。这说明检测触发正确，但恢复器发生了不必要
的过度反应。

据此只在开发阶段做了三类机制修正：

- 将“立即冻结”和“确认后几何恢复”拆开，短故障可取消；
- 加入发送臂已释放后的接收边恢复，并按当前关系选择验证 `both` 或仅验证 receiver；
- 补齐终端位姿、控制关系边、估计置信度、专家状态和信息边界 trace，并对双臂最终监督动作
  做状态切换边界限幅。

这些修正均在正式 seed 冻结前完成；没有根据未来正式结果调参。

在线恢复时间分别为：空抓 1.78–1.80 s，短丢失 0.28 s，交接中强丢失 2.10–2.12 s，
释放后强丢失 2.64–2.66 s。所有强故障只使用一次重抓。全体恢复 trial 的最大施加动作和
监督动作跳变均为 0.050 m，最大恢复段末端速度为 0.4626 m/s。在线强丢失的一条 trial 在
重抓后出现两步估计器 `CANDIDATE_LOST`，监督器冻结后取消；物理接收边没有再次断裂，原始
事件完整保留在 trace 中。

此前同一开发流程的四方法完整矩阵（seed 8608–8610）表明：时钟专家在空抓和交接中强
丢失上 0/6 成功且 6/6 不安全释放；关系门控在三类强故障上 0/9 成功，但没有不安全释放；
在线和 Oracle 恢复均为 15/15 成功。该矩阵早于最终双臂输出边界限幅，因此只用于开发机制
比较，不能与后续正式 cohort 混合统计。

## 6. 审计范围与下一步

硬审计检查精确文件成员、源码/配置/数据哈希、实验指纹、逐步数组长度和有限性、终端任务
重算、故障物理成立、关系指标重算、恢复指标重算、在线/Oracle 信息边界、正常误触发、
短故障过度恢复、giver 保持、计划释放前再次丢失、恢复时间、动作跳变、末端速度和重抓次数。

开发结果只允许冻结正式协议，不计入正式成功率。下一步将在提交实现检查点后，用未见 seed
预注册四方法五条件正式矩阵。正式结果出来前，仍不开始黑盒双臂学习策略训练。
